# Architecture Assumption Delta: dimension review

日付: 2026-09-30。独立レビュー。外部探索・実験・最終Architecture選定は行っていない。
根拠: [既存Coverage Audit](2026-09-29-architecture-search-space-coverage-audit.md) §2.1、D01–D47、§7–9、§12。
本レビューはbaselineの「別の問いとして代案を比較する価値」を独立性の基準にする。完全直交は要求しない。

## 1. D48は追加が妥当。ただし「起動条件と仕事の成立」に限定する

- 独立した問い: どの観測・条件・要求を、どの範囲の保守作業を開始する理由として受理するか。
- 対比例: 同じ資産、変更通知、権限、queue、実行手順を使っても、変更ごとに開始する方式と、関連変更をまとめて条件成立時に開始する方式では、作業集合と開始理由が変わる。
- さらに、同じ通知経路で「AとBが一度でも到着」と「同じ対象・観測窓のAとBが成立」を変えられる。message transportだけではこの差を記述できない。
- 既存へ吸収する代替: D11に開始前のguard、D42にadmission、D44に保守triggerを加え、D39/47へ参照を張る。表現は可能だが、作業成立の判断が複数行へ散り、比較が抜けやすい。
- 追加理由は新protocolの存在ではなく、この独立した制御判断を比較・検証する必要性。event以外に、要求、schedule、状態差分の照合も同じ問いへ含む。
- **所有境界**: D48はtrigger policy・相関条件・発火/抑止の選択を持つ。時刻の意味はD47、配送と再接続はD39、実行順と予算はD42、実行の重複作用はD12、許可はD40に残す。
- event IDによる通知重複排除と、同じ意味操作の二重作用防止は別。後者をD48だけで解決済みにしない。

## 2. D49は追加可能だが、広い「Materialization」では独立性が弱い

- snapshot、cache、派生生成、選択、編集反映を一括でD49へ移す案には反対。それぞれD20/31/46/30/18–22に既存の問いがある。
- 狭い問いへ限定する: **特定の作業主体・作業期間へ、どの資産版・参照・中間状態を利用可能として結び付け、いつ更新・引継ぎ・解除するか。**
- 対比例: 同じ検索結果、固定版、変換、保存先、権限でも、各turnで再取得する構成と、task単位の作業集合を継承する構成では、再開・委任時に利用可能な情報が異なる。資産の版整合性とcontextへの結び付けの寿命は別の選択である。
- 別の対比例: 同じfileがworkspaceに存在し、toolから取得可能でも、選択領域だけがmodel-visibleな場合と、必要な参照を再取得できる作業manifestが渡る場合では、同じmodelの実現結果が変わり得る。
- この反例を単に「harnessが賢い/賢くない」と説明すると、何が引き継がれたかを評価条件として固定できない。
- 既存へ吸収する有力な代替: D12/20/30/31/38/44/46を束ねるworking-context profileを設け、独立次元は増やさない。contextが常に一つの実行instanceの一時stateなら、この案で十分。
- 独立行を勧める条件: 一つの実行で複数contextを使う、同じcontextを複数実行・主体へ引き継ぐ、または表示・モデル入力・永続保存を別々に管理する選択を実際に比較する場合。今回の入力はこの条件を満たす設計候補を増やす。
- **所有境界**: D49は作業集合へのbindingとその寿命を持つ。鮮度判定はD20/31、派生変換はD46、アクセス権はD40、writebackの受理はD05/18–22へ参照する。D49はこれらの保証をcontextに適用・追跡する。
- UIに表示されたこと、modelが読めること、modelが実際に読んだこと、意味を正しく使えたことを一つの状態にしない。

## 3. CACは新しい設計次元にせず、変更試験を束ねる評価属性にする

- baseline §9は変更波及、model portability、migration、意味保持、再検証費を既に含む。「変更へ強い」だけでは新規性がない。
- 追加価値は、**下位の能力改善で不要になった補助構造を除去する費用**と、**同じ意味契約を保つ変更がどこまで上流へ波及するか**を明示的な試験にする点。
- 比較単位はmodel/harness/protocol/runtimeの交換シナリオ。変更したasset・adapter・profile・validator、再評価対象、失われた保証、費用を別々に数える。単純な加重総合点はまだ不要。
- 「canonicalを一切変更しない」を勝利条件にしない。能力・作用の意味が本当に変わるなら意味版更新が正しい。逆にIDを維持しただけで意味保持と判定しない。
- 低能力環境へのdegradeは、品質閾値内の対応、明示的な部分対応、拒否を区別する。欠けた意味を隠して実行できたことをCAC改善としない。
- adapterへ処理を集めれば良いとも限らない。複雑なadapterが新たな長期負債となる費用も含める。

## 4. F1–F8、R0–R7とinterface評価へ与える変更を限定する

- D48/D49の追加だけではF9は不要。起動方式と作業contextは各familyの組合せ候補であり、F3のevent authorityやF6のdurable instanceを必然化しない。
- F1/F7は固定した作業集合と失効、F2/F3は現行状態と作業snapshot、F4は異なるscopeの混在、F5/F8は生成・変換条件、F6はcontextとinstanceの版の対応を重点確認する。family優位性の実証にはならない。
- R1に作業成立と変更受理の境界、R3に重複通知・中断・再開、R5にcontextの継承・更新・失効を足す。これらを先行させる根拠は新しい運用仮説であり、MCP採用判断ではない。
- R4にはcontext編集の意味・authority、R6にはCACの読取器/補助構造除去、R7には同一modelでharness/contextを変える比較を加える。R2を後退させる実測根拠はまだない。
- R0は継続し、R8追加やR全体の全面並べ替えは不要。各追加試験が既存の対立仮説をどれだけ識別するかで小さく実施する。
- interfaceの8層は数値の掛け算ではない。経路を固定した到達可能性と、その経路でのmodel実現率を引き続き分ける。作業集合の内容・binding時点・実行環境を再現条件に追加する。

## 統合担当への推奨

D48は独立行を追加し、D49も上記の狭い定義なら独立行として追加する判断を支持する。両方とも他次元の保証を奪わず、cross-referenceで接続する。CACは既存評価を具体化する差分とし、追加次元や新familyの根拠にはしない。D49の選択が既存profileの束としてしか観測できなかった場合は、将来再統合できる暫定性を明記する。

主稿§5の初稿に対する具体的修正: D49の「都度最新版対起動snapshot」はD20の選択、「payload展開失敗対完全」はD25/D43の結果なので、それだけでは独立性の根拠にならない。選択資産・固定版・変換・読取契約を保ったまま、作業集合のbinding寿命、主体間引継ぎ、実行とcontextの多対多関係を変える反例へ差し替えることを推奨した。
