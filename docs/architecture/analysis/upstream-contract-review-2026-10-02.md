# AKR: 上流判断と下流へ渡す保証の独立整理

2026-10-02 JST · upstream reasoning review · analysis draft

**これは既存資料からの研究上の論理推論であり、独立実証ではない。** 外部調査、実験、既存資産の改修、Canonical・DB・IR・schemaの選定は行っていない。

## 読み方と根拠

- **必要保証**: ユーザーのPurpose / Principles / Constraintsに明記された要求、またはそれを満たすための範囲を限定した導出。後者には「導出」と付ける。実現済みの保証ではない。
- **追加仮定**: 要求からは一意に導けず、採用するなら別途根拠が必要な前提。以下では採用しない。
- **候補依存の判断**: 論理Architectureを比較して決める責務・境界。下流へ渡す範囲は、その選択後に具体化すべき契約であり、共通schemaや固定layerの採用ではない。
- 原資料 **P** はこのセッションでユーザーが提示したPurpose / Absolute Principles / Hard Constraints。既存分析の推奨をPと同格には扱わない。
- **C**: [Coverage Audit](2026-09-29-architecture-search-space-coverage-audit.md)。D01–D47、§3/7/8/11。
- **D**: [Assumption Delta](2026-09-30-external-landscape-assumption-delta-audit.md)。D48/D49、起動・context・CAC。
- **M**: [盲点総括](2026-10-01-blindspot-synthesis-and-research-meta-analysis.md)。B1–B7。
- **L**: [AI-native・規模・層への実現](2026-10-02-ai-native-scale-and-layer-realization-delta.md)。§2–7。

以下は10の判断束である。新しい設計次元でも、相互排他的なFamilyでもない。

## U01 管理対象と資産の境界

- **根拠 / 必要保証**: Pの蓄積・再利用・改修・置換・廃止と、C D01–D03。何を変更・評価・利用する対象として扱ったかを追えることが必要（導出）。登録前に全意味を確定する要求はない。
- **追加仮定**: 全対象が完結した手順である、登録・意味版・配布・評価の単位が一致する、発見物はすべて能動的に保守すると有益である。
- **対立仮説 / 候補依存の判断**: 完結した方法を主単位にする／primitive・制約・生成器・評価器を別対象として構成する／用途に応じて両者の関係を管理する。
- **判断を変える反例**: 一つの条件変更で多数の手順copyを改修する一方、共通部品化すると用途固有の停止条件を誤って共有してしまう。どちらの粒度も一律には優位でない。
- **下流へ渡す保証の範囲**: その候補が扱う対象種別、操作・評価の単位、分割・合成後に残す関連を明示する。未評価のcaptureは利用・採用済みへ自動昇格させない。
- **未知**: 実際の対象分布、適切な粒度、資産利用そのものの増分便益。M B1/B2の実例が必要。

## U02 同一性・意味変更・版

- **根拠 / 必要保証**: Pのversion・rollback・意味変質検出・複数AIのdivergence検出、C D04/D15/D17。変更前後を特定し、同一性や互換性の主張を何に基づいて用いるか識別できることが必要（導出）。
- **追加仮定**: 同じIDまたはdigestなら同じalgorithm、全候補が共通意味版を持つ、すべての意味変更を自動決定できる。
- **対立仮説 / 候補依存の判断**: 共通の意味契約と改訂規則を持つ／候補固有の意味版を持ち範囲付き対応を記録する。系統の継続、内容の一致、用途内の互換性をどこで判定するか。
- **判断を変える反例**: 本文bytesは同じでも解釈規則が変わる。逆に表記変更でbytesが変わっても、指定用途の性質は保持される。分割・合流は単一IDの継続だけでは表せない。
- **下流へ渡す保証の範囲**: 対象版と解釈条件、主張する同一性・互換性のscope、根拠、未判定を追跡可能にする。ID方式やversion番号の規則は選定しない。
- **未知**: 自然言語資産の意味差判定、対応主張の維持費、意味版と評価版の適切な分離。

## U03 意味を決める根拠と共通化

- **根拠 / 必要保証**: Pのmodel/environment independence、explicit semantics、重要意味の二重管理回避、C D05–D07。ある用途で何を規範として読むか特定できることが必要（導出）。一つの共通意味モデルは明文要求ではない。
- **追加仮定**: 全資産を一つのIRへ無損失に写せる、共通規範なら物理形式も一つ、複数表現なら独立した意味編集も常に必要である。
- **対立仮説 / 候補依存の判断**: 共通意味から各用途へ実現する／候補固有の意味と限定した対応を保持する／共通管理契約と固有意味を併用する。
- **判断を変える反例**: 共通化すると対話・不確実性・作用の一部を失うが、native保持では採用scopeが重複し、同じ要求への相反する判断を解けなくなる。
- **下流へ渡す保証の範囲**: 規範内容と採用判断のauthority、適用scope、対応不能・矛盾時の扱いを指定する。説明・検索表現から規範を無条件に書き換えない。
- **未知**: 共通化で失う意味、native維持の同期・照会費、scope包含の判定可能性。

## U04 未知・適用・合成

- **根拠 / 必要保証**: Pの適用条件・入出力・依存・競合・停止の明示とvalidation、C D07–D12/D32。利用時の要求と確認できた範囲を区別し、未確認を確認済みと扱わないことが必要（導出）。
- **追加仮定**: 不在は常に偽、型がつながれば合成可能、全依存は静的、全自然言語条件の真偽を機械判定できる。
- **対立仮説 / 候補依存の判断**: 登録・公開時に可能な範囲を検査する／利用時のprobe・証拠で判定する／両者を組み合わせる。未判定時に許す調査・限定利用・停止の境界も比較する。
- **判断を変える反例**: 入出力は一致しても作用が競合する、各方法は停止しても相互呼出しが停止しない、適用条件が不明なことを不適用と混同して有用な候補を排除する。
- **下流へ渡す保証の範囲**: 判定した条件・時点・環境・根拠、残る未知、合成が要求する性質を表せる契約。固定の状態名や万能checkerは要求しない。限定利用は必須条件の黙った省略を許す意味ではない。
- **未知**: 条件を形式化できる範囲、誤受理・誤拒否の費用、意味上必要な依存と宣言依存の差。

## U05 AIによる自己改修・評価・採用authority

- **根拠 / 必要保証**: PのAI primary maintainer、自動改修/migration、regression検出、C D18/D32/D37/D40、M B4。判定対象と判定根拠を一緒に変更しても、何を基準に受理したか追えることが必要（導出）。
- **追加仮定**: AI同士の一致が独立正解、旧checkerは永久に正しい、checker変更はすべて人間承認、全項目の版があれば評価根拠も十分である。
- **対立仮説 / 候補依存の判断**: 資産・checker・採否規則を段階的に受理する／結合した変更として受理し旧新の判断差を検査する。誰にどのscopeの規範変更を許すかを別に定める。
- **判断を変える反例**: 資産から条件を落とすと同時に新checkerからその検査を消し、全試験に合格する。意図した規範変更なら正当な場合もあるため、旧checkerとの不一致だけで拒否できない。
- **下流へ渡す保証の範囲**: 提案・評価・採用・規範変更の資格とscope、使った対象/入力/評価根拠、旧新の判断差・変更理由を区別する。独立正解がない領域はその限界を残す。
- **未知**: 自然言語の評価根拠の妥当性、共通誤りの検出力、自己改修で許せる同時受理範囲。

## U06 論理責務の分割と全体保証

- **根拠 / 必要保証**: Pの競合・依存破壊検出とrepair、C §3/D19–D22、L §5、M B3。採用した保証が複数責務の境界で失われないことが必要（導出）。全体を一つのtransactionにする要求ではない。
- **追加仮定**: 同名のstatusは同じ意味、局所的な成功を足せば全体成功、安定したlayer分割が一つだけ存在する。
- **対立仮説 / 候補依存の判断**: 共通の受理境界で不変条件を成立させる／scopeごとの局所受理と利用・合成時の検査で成立させる／保証ごとに配置を変える。
- **判断を変える反例**: registryは撤回、bundleは正しい旧内容、jobは起動時検査済み。継続jobにも撤回を効かせるpolicyの場合だけ、実行時の保証が破れる。policyが違えば同じ状態は障害でない。
- **下流へ渡す保証の範囲**: 守る不変条件、対象集合、効力の時点、誰が照合・拒否・修復するか。固定サービス数、transport、全層原子性は指定しない。
- **未知**: 調整が必要な操作、許容する古さ、部分成功からの回復、責務を分ける便益と接続費。

## U07 定義・作業・外部作用の寿命

- **根拠 / 必要保証**: Pのchat/agent等への適応、rollback/repair、C D11–D14/D35/D43、D D48/D49。何が再開・復元・補償できるかを区別することが必要（導出）。永続workflow engineの採用は導けない。
- **追加仮定**: 一task一context、通知受領は完了、定義をrollbackすれば外部作用も戻る、再実行は常に安全。
- **対立仮説 / 候補依存の判断**: 保存資産から必要時に再構成する／中間状態を保存して継続する。起動、実行、作業集合、外部作用の寿命をどこまで独立させるか。
- **判断を変える反例**: 公開済みだが完了記録前に停止する。旧定義のjobが新しい実行環境で継続できない。古い通知の再送が別の改修を二重に発生させる。
- **下流へ渡す保証の範囲**: 操作・jobの成立条件、再開に要る状態、完了の意味、重複/中断/補償の扱い。順序・exactly-once等は必要性と実現条件を確認した範囲だけ要求する。
- **未知**: 実際に必要な継続性、作用の照会・補償可能性、状態保持と再構成の長期費用。

## U08 選択的取得と利用可能性

- **根拠 / 必要保証**: Pの大量資産と全資産を毎回contextへ入れない制約、C D28–D31/D38、D D49、M B1/B5。必要なものを発見・選択・取得できる経路が必要。検索結果の存在だけでは利用可能性を満たさない。
- **追加仮定**: 宣言closureが意味上十分、未利用は無価値、直接提示との差は検索器単独の効果、全依存を必ず一括ロードすべきである。
- **対立仮説 / 候補依存の判断**: 選択時に依存集合を固定する／必要時に解決・取得する／用途別に両者を使う。検索・提示・実ロード・利用を別に評価する。
- **判断を変える反例**: 検索した本文は存在するが必須条件を含む参照が取得不能。逆に条件付き依存をすべて取得すると処理予算を尽くす。上位露出だけを改修すると選択偏りが強まる。
- **下流へ渡す保証の範囲**: 何を選び実際に利用可能にしたか、未取得・省略・古さ・予算制約を区別する。部分取得を、意味上の条件充足と同一視しない。
- **未知**: 実query、意味上必要な集合、asset利用の増分便益、長期の選択偏りと誤選択費。

## U09 GitHub管理と分散した実体

- **根拠 / 必要保証**: PはGitHubを変更履歴・version・branch・rollbackの管理基盤とする。C §7は固定commitと候補・採用状態等の対応を要求する。その具体的実現は候補依存であり、単なる定期backupでは管理責務を果たさない。
- **追加仮定**: 全payloadをGitHub内へ保存、Git commitが外部store・実行状態・作用まで原子的に確定、digestさえあれば旧内容を復元可能、保存場所がauthorityを決める。
- **対立仮説 / 候補依存の判断**: Gitで管理する変更を外部へ反映する／外部の受理状態をGitの固定履歴と対応付ける／公開集合を境界に結ぶ。各案の未完・確定・利用可能の扱いを比較する。
- **判断を変える反例**: Git上の参照は健全でも外部payloadや旧readerが失われる。外部更新だけ成功してGitへの対応がなく、branch上の候補・採用構成を追えなくなる。
- **下流へ渡す保証の範囲**: GitHub上の固定履歴から何の内容・解釈・依存・採用判断を管理するかと、取得・保持・復元の経路。復元不能な実行作用を隠さず、全状態のGit格納も要求しない。
- **未知**: 公開境界、payload保持、Gitと外部storeの照合・復旧費、旧新scopeの並存方法。

## U10 長期変化・容量規模・保守評価

- **根拠 / 必要保証**: Pの長期保守、model/environment independence、移行可能性、大量蓄積、L §3/6/7。資産数だけでなく依存・容量・更新・利用条件を変えて保守可能性を評価する。数百GB/TB/PBは探索条件で、実容量・初期必須目標ではない。
- **追加仮定**: model交換は常にadapterだけで吸収、PBなら特定DB、AIが生成できれば保守も安価、現在のprofileで劣後なら資産全体を廃止、全将来環境と完全互換。
- **対立仮説 / 候補依存の判断**: 安定した上位契約から各層を生成する／各層の固有契約と版付き対応を保持する／負荷・用途別profileを使う。保存・更新・再検査・撤去の費用を比較する。
- **判断を変える反例**: 大容量でも作業集合は小さい。小容量でも依存が密で一変更が全再評価を起こす。高能力model向けの補助構造除去が、local用途の必須情報まで失わせる。
- **下流へ渡す保証の範囲**: 保持すべき意味/identity/lineage、許容する部分対応・拒否、対象負荷・用途・障害条件、変更波及を測る範囲。ゼロ移行費、無期限保存、普遍的性能は要求しない。
- **未知**: 実利用分布、将来変化、許容費用・損失、closure/更新の分布、追加抽象化と交換可能性の総費用。

## 統合担当への要点

1. **上流契約で未確定なのは意味の内容だけでなく、保証のscope・時点・判断主体である。** これを置かずにlayerを先に区切ると、同名のstatusや局所成功を全体保証と取り違える。
2. **共通化の範囲、受理境界、変化を吸収する境界は別の判断である。** 共通意味を選んでも全体一括受理は導けず、native保持を選んでも共通の管理契約が不要にはならない。この三つを候補の組合せとして比較する価値がある。
3. **AIの自己改修には、道具と判定根拠が同時に動く条件を含める必要がある。** 版管理、AI同士の同意、旧checker固定のいずれも単独では解けない。旧新の根拠と規範変更の理由を比較できる範囲を、論理構成ごとに示す。

10論点を既存次元に対応付けられることは、分離完成や基礎理論完成の証拠ではない。次の統合では少数の論理構成ごとに、採用する追加仮定、責務の割当て、成立しない条件、必要な実例を並べる。ここで挙げた反例は候補を判別する研究材料であり、障害の発生率や最終方式の優劣を示さない。
