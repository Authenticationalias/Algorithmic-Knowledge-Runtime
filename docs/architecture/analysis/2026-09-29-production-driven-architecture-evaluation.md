# AKR: 実運用とArchitecture探索を両立させる設計評価

日付: 2026-09-29  
Artifact ID: AKR-ANALYSIS-20260929-PRODUCTION-01  
状態: 提案。Architecture・schemaの採用決定ではない。  
今回の範囲: 分析、候補整理、最小運用baselineの導出。実装、運用開始、既存資産のmigrationは含まない。

## 0. 結論

**実際の登録を続けながら、複数の表現・Architecture候補を育てる方式は成立し得る。推奨する最小構成は、薄い共通の管理情報、固定版の保存、用途ごとの採用判断、観測記録を共有し、意味モデルと表現方式の競争を残す構成である。**

Single Canonical RepresentationもSingle Canonical Formatも必須ではない。一方、同じIDを付けるだけでは複数表現の意味の一致は保証されない。必要なのは、次の問いに答えられることだ。

1. どの方法の系統、どの意味上の版、どの表現の固定版なのか。
2. その意味を読む根拠は何で、どの範囲について採用されているのか。
3. 別表現との関係について、何を主張し、何を検証し、何が不明なのか。
4. 誰／何が、どの入力・基準版・処理から作り、どの判断で利用可能にしたのか。
5. 今回の利用が、どの候補構成と依存集合を使ったのか。

ここではCanonicalを「常に同じ形式」から切り離し、**範囲を指定した意味上の採用判断と、その判断が参照する不変の資料集合**として扱えるようにする。単一のファイル、writer、全資産共通の意味IRを要求しない。

複数表現の冗長性は、AIの生成・同期・検証・修復費用と、再利用性能・比較可能性・将来の選択肢を残す価値で評価する。人間による反復編集の負担を主要理由に排除しない。ただしAIによる管理も無償・無誤りではないので、生成対象と比較予算を定める。

## 2. 四種類のCandidateを分離する

| 種類 | 比較する対象 | 例 | 単独では答えられないこと |
|---|---|---|---|
| Architecture candidate | 意味の置き方、書込み責任、同期、公開、保守の全体構成 | 一つの主表現から生成／複数規範表現／独立意味モデル | 特定モデルに最適なprompt |
| Representation candidate | 一つの方法をどう記述するか。意味の構造とencodingを区別 | 文章と契約／型付き手順／graph／特定schemaのJSONやXML | 更新を誰が確定するか |
| Runtime candidate | 表現をどう解釈・実行するか | 段階対話、tool loop、実行plan、コード、モデル別adapter | どの資産を発見できるか |
| Retrieval candidate | 候補をどう見つけ、順位付けし、取得するか | 属性filter、語彙検索、vector、関係探索 | 見つかった方法が意味的に正しいか |

Storageも別軸として、各候補の構成に記録する。JSONとPostgreSQL、RDFとvector indexを同じ種類の候補として順位付けしない。

比較runには、Architecture、representation profile、storage、retrieval、runtime、model、validatorの各固定版を含む構成IDを付ける。一度に複数を変える場合は全体構成の比較とし、差を特定の要素だけの効果と主張しない。

## 3. 上流Architecture候補

以下は探索用の候補IDであり、既存repositoryの採用状態を表すものではない。

| 候補 | 意味と変更の扱い | 利点 | 主な費用・失敗 | 評価する仮説 |
|---|---|---|---|---|
| ARCH-A: 主表現から生成 | 意味版ごとに一つの主表現を採用し、他表現を生成 | 同期方向が明快。影響追跡・再構築が比較的単純 | 主表現が表せない情報や編集方法に制約。変換器へ費用が集中 | 一つの規範表現を維持する方がAI保守総費用が低い |
| ARCH-B: 複数の規範表現を共同管理 | 一つの意味版を、範囲と優先規則を持つ複数資料から定義 | 表現ごとの強みと独立改修を活かせる | 矛盾検査、変更の合成、範囲管理の負担 | 表現ごとの局所改修の便益が同期・検証費用を上回る |
| ARCH-C: 候補固有の意味モデルを並存 | 共通ID・出典・来歴を共有し、候補ごとにnativeな意味モデルを維持 | 共通IRによる探索制限を小さくできる | 対応不能・意味差分・重複評価・移行の負担 | 各候補固有のモデルによる便益が対応管理費を上回る |

**推奨baselineは、これらを収容できる薄い管理層である。** 最初の個々の資産でARCH-A型の主表現を選ぶことはできるが、それを全候補の必須入力へ固定しない。ARCH-Bは小さな資産群から試し、全資産について自由な双方向同期を初期実装する必要はない。ARCH-Cは同じ原資料から独立に登録する比較経路を確保する。

日常運用では、対象用途について採用済みの表現または整合した表現集合を選ぶ。その選択規則が矛盾して一意に決まらない場合は、解決を要する状態を返す。実行ごとにAIが「それらしい方」を無記録で正本にする構成は採らない。

共通層が持つのは、ID、参照、来歴、主張と判定状態、採用scope等の管理上の意味である。汎用の手順graph、型体系、全領域の条件式言語はここに含めない。共通層自身にも版と移行経路を持たせる。

## 4. Identity / Revision / Authority / Lineage

### 4.1 同じIDと同じ意味を区別する

| 概念 | 定義 | 固定する規則 |
|---|---|---|
| Algorithm identity | 方法の系統を指す安定ID | 名前・path・分類から独立。再利用しない |
| Semantic revision | その系統で主張・採用する意味上の状態 | 不変IDと根拠資料、親、採用判断を持つ。hashを意味同値判定にしない |
| Representation identity / revision | 表現系列と、その具体的な固定内容 | payload、解釈profile、digest、対応主張を固定 |
| Authority | この用途・版・scopeで、どの規範や判定を採るか | 作者や保存先から自動推定しない |
| Lineage | 分岐・改修・合流の経路 | 複数親を許容。旧版を書き換えない |
| Provenance | 入力、作成・変換活動、tool、model、設定等の由来 | 由来と品質保証を混同しない |

したがって「Single Semantic Identity / Authority / Lineage」という仮説は、次のように修正すると成立する。

- 共通identityは有用だが、同値性の証明ではない。
- authorityは全システムで一つのファイルに集約せず、scopeごとに採用判断を特定できればよい。
- lineageは一本の鎖に限定せず、相互参照できる履歴graphでよい。
- 不変revision、意味を読む資料、適合関係の証拠が追加で必要である。

初期の登録で意味が十分に確定しない場合は、`captured`なartifactとして受け入れ、semantic revisionへの対応を`unassessed`とする。「何かを保存した」ことを「同じ意味の新しい表現と確認した」ことに読み替えない。

### 4.2 意味を読むためのanchor

semantic revisionは、意味の根拠となる固定資料への参照を持つ。これをここではsemantic anchorと呼ぶ。原文、コード、契約、複数の資料集合のいずれでもよい。共通IRへの変換は条件にしない。

anchor集合には必要な解釈仕様と範囲を付ける。複数資料が同じscopeについて矛盾する場合は、その部分を未解決とし、勝手な優先順で統合しない。限定範囲の採用は可能だが、範囲を明示する。

anchorの意味を変える改修は新semantic revisionを作る。意味保存を検証した形式変換だけならsemantic revisionを維持し、新しい表現と対応記録を追加できる。厳密な境界を判定できない場合は新候補として保持する。

## 5. 表現間の関係をどう扱うか

### 5.1 equivalenceを一つのbooleanにしない

| 関係 | 主張すること | 主張していないこと |
|---|---|---|
| byte identity | 同じ対象bytesである | 内容が正しいこと |
| information-preserving encoding | 指定profile上で値・構造を失わず変換した | 任意の実行環境で同じ挙動になること |
| procedure preservation | 宣言した範囲で手順・条件・制約を保持した | 未記述の性質もすべて同じであること |
| contract conformance | 指定された契約に適合する | 同じアルゴリズムであること |
| observed behavioral correspondence | 指定した課題・環境で対応する振る舞いを観測した | 未試験の入力での一般的同値性 |
| runtime substitutability | 指定profileで代替可能と判定した | 他model・runtimeでの代替可能性 |
| refinement / projection | 詳細化・制約追加、または一部の情報を抽出した | 双方向に置換可能であること |
| related / divergent / unknown | 関連、差異、判定不足がある | 同じsemantic revisionとして使えること |

関係記録には、対象両側の固定版、関係種別、scope、判定方法・版、証拠、未検証範囲、判定状態を持たせる。対称・推移的に扱えるかは関係ごとに定める。異なる評価範囲のA≃BとB≃CからA≃Cを自動確定しない。

同じ整列結果を出す二つの方法でも、手順・計算量・安定性が違えば別の有用なアルゴリズムであり得る。出力テストの一致だけでIDを統合しない。

### 5.2 derivationはequivalenceではない

`derived_from`は作成の由来である。意味保存、品質改善、可逆性は別の主張として記録する。

W3C PROVのEntity / Activity / Agentとderivationは、この来歴を記録する参考になる。ただし`alternateOf`も、同じものの異なる側面との関連を示す広い関係であり、AKRの手続き同値性を証明しない。[PROV-DM](https://www.w3.org/TR/prov-dm/#component5)

### 5.3 version correspondence

semantic revisionとrepresentation revisionの対応は一般に多対多となる。一つの意味版に多数の表現があり、変わらない部分表現が複数の意味版で使える場合もある。対応は別recordとし、型、scope、証拠を通じて管理する。

最低限、意味版、表現版、解釈profile版、adapter版、evaluator版、対応・採用記録版、公開snapshotを区別する。画面上は短いラベルで表示してもよいが、実行と評価は不変IDを参照する。

## 6. 独立変更とsynchronization

**同期の目標は、全表現を常に同じ最新版へ書き換えることではなく、版の対応と利用可能範囲を正しく把握できることである。**

### 基本経路

1. AIは編集元の固定版と意図を記録し、新artifactを作る。
2. 表記変更、契約を保つ実行改善、意味変更、判定不能のどれに当たるかを評価する。
3. 意味変更なら新semantic revision候補を作る。意図と実際の差を区別する。
4. 影響を受ける対応・依存・adapterに更新候補を作る。
5. 対応を検証し、対象scopeの採用recordを基準版付きで更新する。
6. 検索・利用は対応済みの固定版集合を選ぶ。未追随な表現を新意味版として渡さない。

たとえば`ALG-X@S1`に対するA1とB1があり、A2の改善を`S2`として採用した場合、B1はS1の有効な表現として残る。B1のS2対応は`pending`、`unsupported`等で明示する。古い版であることと破損していることを混同しない。

独立編集したB2が新しい意味を持つなら、S1の別表現として上書きせずS2b候補とする。A2とB2を統合する場合は両方を親に持つ新候補を作り、意味の統合を検査する。語句の自動mergeや最終更新時刻だけで採否を決めない。

### 編集結果と取扱い

| 編集結果 | 扱い |
|---|---|
| 意味保存の根拠がある表現変更 | 同じ意味版への新representation revision |
| 契約を保つモデル別実行改善 | 独立したadapter revisionとして評価 |
| 条件・手順・作用・成功基準の変更 | 新semantic revision候補 |
| 対象範囲や保証を緩めたもの | scope付きvariantまたは新意味版 |
| 方法として別系統へ分岐 | 新Algorithm IDとfork等の関係 |
| 意味差分をまだ判定できない | 対応未確認の候補 |

IDの分割・統合・aliasの詳細規則は進化させられる。ただし旧IDを別の意味へ黙って再利用しない規則は今固定する。

同じ意味版へのadapterとして扱うには、入出力契約に加え、semantic anchorで規範とした手順・制約を、宣言した適合範囲で保持する。許される実装上の自由度はprofileに示す。規範手順を別方式へ変更したものは、出力テストが一致しても新意味版またはvariantとして評価する。

### 制御可能な冗長性

全表現間の相互変換を必須にすると変換経路と検証対象が増える。必要な変換だけを登録し、変換元を明示したgraphとして管理する。共通IRを変換の中継点にする候補も比較できるが、全候補に強制しない。

各関係に`対象版・対応状態・最終評価・未追随理由`があり、修復待ち量と費用を測れれば冗長性は管理できる。対応が不明なまま同じ最新版として検索・実行される状態が問題である。

## 7. prompt / adapter / model-specific variantの保存

「生成物」「再構築可能」「独立評価する資産」は相互排他的ではない。由来、再生成可能性、利用上の役割、保持価値を別に扱う。

| 対象 | 推奨する管理 |
|---|---|
| 決定的な索引・表示形式 | 入力とgeneratorを保持した派生物。再構築試験を持つ |
| 決定的に生成したprompt | 派生物として管理できるが、評価で使用した版・設定は固定する |
| AIが独自に改善したprompt | 固定artifactとし、model/runtime/scopeごとの評価を保持する |
| 同じ契約を保つadapter | 元意味版への適合主張を持つ独立評価対象 |
| 契約を変えるmodel-specific variant | 別意味版またはvariant。元資産との関係と差を記録する |

cacheとして削除可能かは、必要な入力・tool・設定・モデルへのアクセスと、許容する再構築品質が確保されているかで決める。確率的な生成はseedがあっても同一bytesを保証できるとは限らない。重要な採用判断の証拠に使った出力は、単に「再生成できそう」という理由で失わない。

保持しても、検索時にすべてをcontextへ入れる必要はない。役割・対象モデル・適合範囲で候補を絞ってから選択する。

## 8. Minimum viable semantic envelope

最小envelopeは存在する。ただし、これは任意の意味を機械的に実行できる最小schemaではなく、**意味の原資料・版・対応・判断を失わず、後から詳しく構造化できる最小管理契約**である。

### 8.1 登録時の必須情報

| 情報 | 最小内容 | 不明の扱い |
|---|---|---|
| identity | namespace付きの永続Algorithm ID、artifact ID | 同一資産か未確認なら仮の別IDを発行し、後から関係を記録 |
| immutable revision | 表現の固定版、親・基準版、digest方式と対象範囲 | 意味revisionへの対応は未確認を許す |
| source | 原資料または取得内容の保持参照とdigest | 由来不明を明示し、登録時点の内容は保存する |
| interpretation | media type、encoding、schema／言語／interpreterの識別・版 | 読めないものはopaqueとして保存し、自動利用しない |
| semantic anchor | 目的・方法を読むための固定資料、暫定説明とその根拠 | 意味の確定を要求せず、仮説・未確認を保持 |
| known constraints | 既知の適用条件、依存、作用、停止条件への参照 | 未調査、確認済みでなし、存在を区別 |
| provenance | 取得・生成・改修活動ID、入力版、tool/model/config参照、時刻 | 取得できなかった項目と理由を明示 |
| disposition | captured／candidate、対応関係の判定状態、採用判断への参照 | 未採用を初期値とし、同値・安全・実行可能と推定しない |

このenvelope自体にprofile versionを付け、未知の任意fieldを失わないようにする。未知の必須機能を黙って無視して実行しない。

原資料を保存するだけでは再利用の契約は成立しない。ただし未完成の意味解析を理由に発見物の登録を止める必要もない。

### 8.2 自動選択・実行前の追加条件

- 対象用途で必要な適用条件、入出力、作用、停止条件が判断できる。
- 採用する意味版・representation版・adapter・依存を固定できる。
- その用途の評価要件を満たすか、不明時の取り扱いが決まっている。
- 対象scopeについて有効な採用判断と現在の利用停止を確認できる。

`captured`から自動利用へ進める条件は、用途ごとに版管理する。全資産に完全な形式証明を要求しない。条件が足りない資産は登録済みのまま追加評価の対象になる。

### 8.3 最小の具体例（論理記録の例。schema採用ではない）

```text
Algorithm: ALG-X
  purpose: 候補を制約で絞り、残りを比較する
  source: SRC-1@fixed-revision

Meaning claim: SEM-1
  parent: none
  anchors: REP-A@a1
  scope: 制約の true / false / unknown を区別する方法

Representation: REP-B@b1
  targets: ALG-X / SEM-1
  derived_from: REP-A@a1
  profile: structured-procedure-profile@p1

Correspondence: MAP-1
  source: REP-A@a1
  target: REP-B@b1
  relation: procedure-preservation
  evidence: EVAL-1@e1
  status: supported-within-scope

Adoption: USE-1
  scope: chat / profile-chat-1
  uses: SEM-1 + REP-A@a1
  evidence: EVAL-CHAT-1
```

REP-Bが`unknown`を合格として扱ったなら、MAP-1の主張に反例がある。保存自体はできるが、SEM-1の適合表現としては採用しない。別の意味変更案として残すか、修復する。

### 8.4 何を今は必須にしないか

全資産共通の型体系、全文の論理形式化、唯一の分類木、共通手順IR、全表現間の可逆変換、全モデルでの実行可能性は登録要件にしない。モデル名をIDやCanonicalな意味の一部に埋め込まない。

## 9. 実運用を止めない最小baseline

必要な論理部品は次の五つで足りる。別々のサービスにする必要はない。

1. **取り込み**: 原資料を固定保存し、envelope付きで受け付ける。
2. **版と対応の台帳**: identity、revision、候補、来歴、適合主張、採用判断を追える。
3. **利用経路**: 採用済みprofileから必要な表現と依存を取得する。
4. **比較の経路**: 対象資産について別候補を生成・改修・再実行する。
5. **観測の記録**: 成功、失敗、不採用、費用、修復を固定版に結び付ける。

baseline開始時は、利用可能な一つの表現で登録を完了し、比較候補の生成は非同期に進められるようにする。他表現の生成失敗や比較待ちで登録全体を停止しない。部分公開は候補ごとの対応状態を含むsnapshotとして明示する。

初期の並存量は、たとえば「通常利用の一方式＋一つの比較方式」を基本に、関係の密な資産群だけ第三候補を加える。これは可逆な運用上の初期値であり、永続的な候補数の上限ではない。計算・検証・修復の実費に合わせて増減する。

新しい実アルゴリズムは、登録時に原資料、初版、変更理由、選んだ利用profileを残す。比較対象にしなかった資産も対象外理由を残し、成功しやすい例へ偏っていないか検査・再抽出できるようにする。理由の記録だけでは偏りは消えないため、現在の選択や検索結果から独立に抽出するcaseも比較集合へ加える。

AIが日常操作を行い、機械的なID・hash・参照検査はtoolに任せる。人間による日常の同期作業を必要とする経路はbaselineに含めない。

## 10. 実運用datasetを評価基盤へ育てる

運用記録、再実行用case、評価集合のreleaseを区別する。運用記録には未判定・再現不能も残す。入力・対象版・環境・判定方法を揃えたものを再実行用caseとし、case集合と評価基準を固定して初めて比較用releaseとする。資産件数に加え、独立した系統の数、操作種別、依存構造、観測期間を記録する。

### 10.1 最初から記録する情報

| 記録 | 最低限必要な内容 | 後から失うと困ること |
|---|---|---|
| 登録・変更 | event ID、入力／基準版、出力版、変更要求、処理、結果 | 何を改善しようとして何が変わったか |
| 変換・同期 | 変換元／先、generator版、意味差分主張、対応状態、待ち時間 | 同期費用と意味変質の発生箇所 |
| 検索 | 問い合わせまたは評価可能な保管参照、corpus/index版、候補、選択、no-match | 発見されなかった資産、誤選択、当時の検索可能範囲 |
| 実行・再利用 | 入出力参照、選んだ資産・表現・依存・adapter・model、結果 | 何を使った時の成功か、どの条件で失敗したか |
| 依存の変化 | 追加・削除・版変更、直接影響と実際の検査対象 | 依存密度と改修の波及 |
| conflict / repair | 両側の基準と変更、競合種別、検出、修復、再試行、結果 | AIによる復旧に要した費用と未解決事項 |
| validation | test/evaluator版、対象scope、pass/fail/unknown、反例 | 採用の根拠と後の判定変更 |
| resource | token、context量、wall time、tool費、CPU等、storage量、欠測 | AI管理費用を含む候補比較 |
| exposure / routing | 適格候補、選択規則、割当、比較・調整予算 | 特定候補だけ有利な仕事を受けた偏り |
| disposition | 採用・不採用・廃止・取消の理由と証拠 | 結果だけを残した場合に消える判断経緯 |

`run_id`で一連の記録を結び、修復は失敗runを参照する。欠測値はゼロや成功として補わない。費用は元の計測単位と課金単価の時点を保持し、後からの換算値と区別する。

全ての詳細traceを永続保存する必要はない。全試行の軽量な結果・版・費用は残し、詳細な入力・出力・tool結果は必要性に応じて保管する。observableな操作と判定理由を記録し、モデルの非公開な内部思考の取得を前提にしない。

Gitのcommit履歴だけでは、検索失敗、生成失敗、破棄された案、費用は復元できない。これらには明示的な観測recordが必要である。観測eventを記録することは、全資産をevent sourcing方式で管理するという採用判断ではない。

### 10.2 保持と公開先

GitHubにはschema、候補定義、採用判断、比較手順、集約結果、再現に必要なmanifestを置ける。大量のtraceや原資料は保持先とdigestを記録して別に保存できる。公開repoへ元会話や入力を自動的に全量公開することを、登録の条件にしない。

保管期限、アクセス範囲、参照不能、削除・匿名化の有無を記録する。再実行に必要な資料が失われた試行は、履歴上存在しても再現可能なbenchmarkには数えない。hashは内容の実体を復元しない。

### 10.3 三種類の証拠を分ける

1. **Production observation**: 実際に利用した候補の成功・失敗・費用。現実の課題分布を捉えるが、使わなかった候補の性能は分からない。
2. **Paired replay / shadow evaluation**: 固定した入力・corpus・依存・環境を、比較候補でも処理する。条件を揃えた比較ができる範囲を明示する。
3. **限定的なproduction routing**: 利用条件を満たす候補の間で、事前に定めた割当方法により実利用を比較する。通常操作を重複実行しない。

外部への作用がある手順のshadowは、記録済みtool結果や隔離した環境を用いる。再現できない部分はそう記録し、実際の成功率と同一視しない。

### 10.4 二つの比較を分ける

**Component比較**では、同じsemantic revisionに対する表現・retrieval・runtimeの差を比較する。意味の同等性が未確認なら、その差も結果として記録する。

**Architecture全体の比較**では、同じ発見原文と変更要求を、各候補へnativeに登録・改修させる。最初にbaselineのschemaへ正規化したデータだけを渡すと、その分割や欠落を全候補へ押し付けることになる。原資料を保持し、この独立経路を残す。

### 10.5 偏りと汚染への対応

- 未選択・未評価の候補は露出とcoverageに残すが、未観測の成否を捏造して成功率の分母へ入れない。実行対象になった登録失敗、timeout等は、事前に定めた試行単位の集計から落とさない。unsupportedとno-matchも別結果として保持し、適格率・検索成功率等のどの指標へ算入するかを先に定める。
- 検索上位に多く出た候補ほど改善機会が増えるため、露出と調整費用を記録する。
- model、tool、環境、価格の変化を、representationの効果へまとめない。
- 学習・調整に使った事例と、未使用の評価事例を分ける。時系列の区切り、同系統資産・近似重複のまとまりも考慮する。
- 同じ課題、比較可能な予算、cold/warm条件で評価し、異なる条件は層別に示す。
- 人工的に複製した件数はstorage・query・queue等の負荷評価に使う。意味の重なりや移行難度を代表する証拠とはしない。
- 実corpusも現在の利用者・用途による偏りを持つ。将来のあらゆるAKRへ一般化した最適解とは呼ばない。

## 11. 候補の維持・採用・停止をどう判断するか

主要な比較軸は、生成、改修、同期、検証、競合解決、repair、検索、実行、migrationの費用と失敗である。人間が読む快適性を主要指標に置かない。監査・介入が実際に必要になった時間は別途記録できる。

費用を、初回構築、通常利用、意味変更への追随、障害復旧、別方式への移行に分ける。単に一回のpromptが短い候補や、現在の同期処理が未実装なので安く見える候補を有利にしない。

候補は用途・資産群・model/runtimeごとに比較する。品質や保持すべき性質を満たした上で、費用・遅延・context量・修復率等にPareto上の優位があるかを見る。異なる役割で複数方式を維持する結論を許容する。

### 運用上の状態と判断

- `candidate`: 仮説、期待する利点、費用、評価対象を記載した案。
- `experimental`: 対象と予算を定めて比較中。
- `current`: 宣言した用途scopeで採用中。最終解でも全用途最良でもない。
- `deprecated`: 新規生成・新規採用を止める対象と時点を指定。既存利用の移行を追う。
- `archived`: 能動的な維持を終え、再開に必要な定義・証拠を保持。

これらを四種類のcandidateと個々のartifactに混同して付けない。たとえばArchitecture案はexperimentalでも、その中のretrieval方式は特定用途でcurrentになり得る。状態recordは対象種別、対象ID、scope、根拠、基準状態、記録版を持つ。

劣後の判断は「同じ用途・条件で比較でき、意味上の必要条件を満たし、追加費用に見合う独自の便益が観測されず、その不確実性も小さいか」で行う。少数例や一つのmodelの失敗だけで方式全体を廃止しない。証拠不足と、劣後の証拠を区別する。

予算超過や修復待ちの増大を理由に新規生成を一時停止する判断は、最終的な劣後判定とは別に記録できる。再開条件を付け、既存利用と参照を壊さない。数値予算は運用費が分かってから設定し、ここで架空の最適閾値は置かない。

## 12. GitHubでの管理

### 12.1 branchとcandidateを同一視しない

branchは作業を分ける手段、candidateは評価対象のidentityである。branch名は変わり、削除もされ得るので、candidate IDと固定commitの対応を別に記録する。

長期候補は、将来たとえば以下のような記録を持てる。これは配置の提案であり、今回の変更で台帳やruntimeを導入するものではない。

```text
docs/architecture/analysis/       分析と履歴資料
docs/architecture/decisions/      scope付き採用・変更判断
evaluation/candidates/            種別ごとの候補定義と固定版
evaluation/runs/                  比較manifestと集約結果
```

current一覧は採用判断から生成する。README、branch名、PR labelにそれぞれ別のstatusを手編集して権威を分裂させない。

実験codeはtopic branch等で分離できる。長期間の維持では、共通部分の更新を追う費用を測る。比較可能な定義・commit・必要artifactを保持し、候補を保存するためだけにbranchを永遠に開いたままにすることは要件にしない。

### 12.2 mainと利用中の構成を区別する

mainにcandidateの説明文や評価結果が含まれても、それだけで採用にはならない。利用側はscope付きの採用recordまたはrelease manifestに固定した構成を読む。文書のmergeと意味・runtimeの採用を別操作として扱う。

GitHubのPRは変更提案・差分・検査を集める機構として使える。draft PRは分析成果を提示する手段になる。[GitHub Pull requests](https://docs.github.com/en/pull-requests/reference/pull-requests)

今回の成果はmainから分けた分析用branchとdraft PRで提示し、既存main、schema、algorithm assets、`architecture-synthesis-v0.2`を更新しない。前回文書と今回入力を、新分析の参照資料として同じ変更に追加する。

### 12.3 履歴があることと復元できること

Git履歴によって以前のcommitを追えるが、参照が失われたobjectやGit外のartifact、利用不能になったmodel/toolまで自動的に復元できるわけではない。保存対象のcommitと必要artifactに保持方針を持つ。

GitHub releaseはtagに基づく配布単位として使えるが、AKRのsemantic revisionそのものと同一視しない。[GitHub Releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases)

内容snapshotをrollbackしても、後から出された利用停止を暗黙に解除しない。実行には内容・依存の固定版と、確認した現在の利用停止記録を残す。

## 13. A / B / C / D: 今決める範囲を分ける

Aは運用開始時の具体的な初期設定、Dはその下に置く後戻りが高コストな規則である。両者は関連するが、交換可能な初期値と長期に守る不変条件を区別する。

### A. 登録開始のために最低限固定するもの

- envelopeの初期profileと、原資料・artifactの保存先。
- ID発行と固定版の取得手段。
- `captured`と自動利用可能の区別、未確認値の表現。
- 最初に使う利用profileと、採用判断の記録先。
- 変更・検索・実行・評価を結ぶ最小event記録。
- 比較候補を非同期に作る経路、対象資産群と初期予算。

実装表記にはJSON等を選べるが、その表記は交換可能な初期値として記録する。この段階で全資産を新しい意味schemaへ移す必要はない。

### B. 並行して育てるもの

- ARCH-A型の主表現から生成する方式と、独立意味モデルから登録・改修するARCH-C型の方式。
- 同じ原資料に対する、文章＋契約、型付き手順、必要な資産群でのgraph等のrepresentation。
- 同じ契約に対するchat、tool利用、モデル別adapter。
- 語彙・構造検索と、検索漏れへの効果が見込まれる他方式。
- ARCH-B型の共同規範表現は、更新衝突や表現固有の利点が見える資産群で試す。

すべての形式をすべての資産へ毎回生成することは初期条件にしない。候補を選んだ理由と生成しなかった範囲を残す。

### C. 実データ蓄積後まで保留できるもの

- 永続的な唯一のcanonical formatの有無。
- 共通意味IR、統一分類、原子化の最適粒度。
- 主storage製品、graph DB/vector DBの必須化。
- repo分割・分散transaction・高並列更新の具体方式。
- 全資産共通の厳密な同一アルゴリズム判定法。
- 各候補の最終順位、永久的な候補数、劣後判定の数値閾値。

### D. 後から変更すると高コストなので今決める規則

1. IDをpath・分類・特定modelへ結び付けず、再利用しない。
2. 採用・評価は不変の内容版を参照し、過去の対象を書き換えない。
3. 原資料、変更要求、変換前の重要artifact、失敗を失わない保持経路を持つ。
4. identity、意味版、表現版、採用状態、由来を混同しない。
5. 未確認、非該当、確認済みでなし、不適合を区別する。
6. 同値性・適合性はscopeと証拠を持つ主張として記録する。
7. 採用を範囲付きの判断とし、競合・取消・基準版を記録する。
8. 複数writerの古い基準に対する更新を検出し、統合後を再検証する。
9. 観測を構成版と結び付け、欠測・不採用・失敗を保持する。
10. 保守基盤の変更を、新しい検査基準だけで自己承認しない。

これらも将来の規則変更を絶対に禁止するものではない。過去の記録の意味を変えず、旧新の対応を明示して移行するための規則である。

## 14. 既存の形式・標準を探索対象へ戻す方法

以下は採用表ではなく、どの仮説を調べるための候補かを整理する表である。

| 候補群 | 主に評価する役割 | 次の評価で確かめる点 |
|---|---|---|
| JSON / YAML / XML / Markdown | encoding、規範文章、構造化record | AIの局所変更・検査・修復費用、情報の取り落とし |
| JSONL / Parquet | 観測・交換・分析用の記録表現 | 追記、部分読取、schema進化、移送費用 |
| SQLite / PostgreSQL / DuckDB | 保存、query、観測分析 | 更新頻度、transaction、比較snapshot、Git管理との接続 |
| RDF / JSON-LD / graph DB | 関係表現、語彙接続、多段探索 | 依存・来歴・適用条件の表現とAIによる保守費用 |
| vector index | retrieval | 語彙検索に対する追加の再現率、誤選択、維持費 |
| event sourcing | 更新の権威と再生方式 | 過去eventの解釈維持、repair、現在状態の再構築費 |
| typed DSL / IR | 本体の構造化、静的検査、実行 | 表現できない手順、形式化費、意味保存 |
| Protocol Buffers / CBOR | 交換・配布・runtime表現 | 通信・読込費、schema進化、比較・検査の費用 |
| S1000D | moduleの識別・状態・適用・品質管理の設計 | AKRへ必要な部分だけ導入した場合の便益と負担 |
| DITA | 再利用単位、参照、条件付き展開 | AIが保守する部品化・展開と意味検証への寄与 |
| OSLC | lifecycle resource間の接続・構成管理 | 異なる保存・実行環境を結ぶ必要性と導入費 |
| W3C PROV | 由来・活動・責任・派生の語彙 | 最小envelopeからの対応付けと来歴query |

S1000Dは識別・状態部と内容部を持つdata moduleを扱い、CSDBの具体機能まで一意に定めるものではない。[S1000D公式概説](https://s1000d.org/?page_id=2)

DITAにはtopic、map、参照、条件付き処理等があり、単なるXMLの別表記として比較するだけでは不十分である。[DITA 1.3 specification](https://docs.oasis-open.org/dita/dita/v1.3/os/part1-base/archSpec/base/ditamarkup.html)

OSLCにはresourceのquery、変更追跡、構成管理等の仕様群がある。AKR全体の意味schemaそのものとは区別して評価する。[OSLC specifications](https://open-services.net/specifications/)

これらを人間向けの用途から生まれたという理由で排除しない。AIが生成・保守する際の検査可能性、対応関係、実際の費用で評価する。今回、それぞれを実装した性能比較や適合性試験は行っていない。

## 15. 推奨する開始順序と確認基準

### 段階0: 今回

分析artifactとして保存する。前回案、既存v0.2候補、本案を区別して参照可能にし、実装やmigrationの採用決定へ読み替えない。

### 段階1: 次に運用を始める際の最小作業

envelope profile、ID・固定版・原資料の保存、採用record、最小観測recordを用意する。新規資産から適用し、既存資産には必要になった範囲から対応を加える。既存IDを振り直す全件migrationを開始条件にしない。

### 段階2: 実登録と限定的な並行比較

実際に発見したアルゴリズムを登録する。同じ原資料から別候補を作り、登録・改修・検索・再利用・repairを観測する。小さな実corpusでも判断できる、参照欠損、同期不能、情報欠落、費用の異常を先に修正する。

### 段階3: 蓄積した履歴から再評価

固定したcorpusと変更課題を作り、component比較とArchitecture全体の比較を行う。役割別の採用を更新し、不要な新規生成を止める。必要な旧artifactと結果を保持し、廃止を取り消す条件も残せるようにする。

### 最小の運用確認

- 新規登録を、他表現の生成失敗で失わない。
- 一つの表現の変更が意味変更か未確認かを記録できる。
- 同じ意味版を主張する二表現の矛盾を、無条件に上書きしない。
- semantic revisionとrepresentation revisionの取り違えを検出できる。
- 二つのAIによる同じ基準からの変更を別々に保存・比較できる。
- 一つの検索・実行・修復の対象版と費用を辿れる。
- ある候補の新規生成を止めても、登録と既存利用を継続できる。
- 索引が失われても、必要なenvelope・原資料・採用判断を復元できる。
- 旧snapshotへ戻しても、利用停止が暗黙に解除されない。

これらはbaselineの整合性確認であり、長期的な最良Architectureの証明ではない。

## 16. 未確定事項と最終判断

未確定なのは、各候補の意味表現力、現実の依存密度と改修頻度、モデル別の適合性、同期・repair費用、利用目的ごとの品質閾値である。これらは実登録を通じて観測し、必要な比較を追加する。

**今固定すべきものは、一つの最終形式よりも、意味・由来・版・採用判断を取り違えず、独立した候補の結果を後から比較できる条件である。**

薄いenvelopeを共通にし、候補固有の意味モデルとnativeな編集経路を残す。通常利用のための採用判断を持ちつつ、候補ごとの並行生成・独立改修・限定的な利用を可能にする。この構成を、実運用開始とArchitecture探索を両立する最小baselineとして推奨する。
