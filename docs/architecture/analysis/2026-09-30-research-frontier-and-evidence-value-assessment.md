# AKR: 追加探索と実験へ移る境界の評価

2026-09-30 · upstream research assessment · analysis draft

## 0. 判断

**次は、意味・合成と評価の成立条件に限定した外部補完を、小さなAKR事例の収集と並行して行う。その事例を使い、既知のmutation・context・中断の問題を比較する段階へ移る。** Landscape全体のclosureを待つ必要はない。

これは新しい探索・実装を一括で開始する決定ではない。今回の成果は、既存証拠に基づく研究上の判断である。

- 外部探索で大きく更新される余地が残るのは、**何を一つの資産として扱い、適用・合成・生成をどう意味付けるか**と、**どの評価証拠を、どの資産・評価器・datasetの版に対して有効とするか**。F5/F8と一部F4の比較に直接関わる。
- mutation、stale state、transaction、通知・再試行、durable executionには、比較を始めるための反例が既にある。次に不足しているのは主に、AKRの対象と成功条件を固定した観測である。
- trust/revocation、semantic query/ontology evolution、industrial lifecycleには外部補完の余地がある。ただし、具体的な照会、採用権限、配布、保存の判断に結び付く時点で範囲を絞る。
- reuse / integrate / buildは、候補製品の一括選定ではなく、**一つの保守作業を成立させる能力と接続境界**から評価する。独自に意味policyを決める必要があることは、独自softwareを作る必要があることと同じではない。
- D01〜D49とF1〜F8は暫定基準として安定させる。R1先行は機構の確認として維持し、R3は途中状態・対話の継続・外部作用のどれを保つ必要があるかに応じて具体化する。R0/R2/R4と評価条件の整理を、Family比較の前提として前へ出す。

## 1. 範囲と基準

基準は[Coverage Audit](./2026-09-29-architecture-search-space-coverage-audit.md)と[External Landscape / Assumption Delta Audit](./2026-09-30-external-landscape-assumption-delta-audit.md)。後者を保存したcommitは `36a38dd1ef6a5fee360ee1b3b2f5f9a9534c87eb`。過去分析の再導出・上書き、全面Coverage Audit、追加の広範なLandscape Scanは行っていない。

新しい入力はユーザーの次の問題提起である。

1. R1/R3/R5への証拠集中が、探索範囲によるselection effectを含む可能性。
2. Family間で証拠の量・種類が異なること。
3. 既存OSSとの重複、統合の残課題、独自実装の必要範囲が未評価であること。
4. 外部探索、実験、実運用観測のどこへ次の研究費を使うべきか。

今回行ったのは、既存の証拠と未解決事項の再分類、および現在の登録事例の限定確認である。外部projectの新しい性能・運用事実を追加していない。二つの独立した抜粋を補助資料にした。

- [Familyごとの証拠inventory](./research-frontier-family-evidence-2026-09-30.md): 証拠が支える部分問題と、Family全体を識別するための不足。
- [残る問いと必要な証拠](./research-frontier-question-evidence-2026-09-30.md): 文献等で判別可能、AKR実例が不可欠、両方必要という分類。

これらの抜粋は今回のDelta Auditを中心にしている。基準Coverage Audit §4.2で既に読んだNix/Bazel、TUF、SLSA、RO-Crate、OWL/SPARQL、MLIR変換、egg等の概念・仕様上の根拠も考慮した。「今回の外部運用例が少ない」を「これまで何も調べていない」へ読み替えない。

## 2. 証拠の非対称性とselection effect

### 2.1 確認できる偏り

今回の調査はmemory/registry、events/distributed state、assets/provenanceという分担だった。この入口では、改修、同期、履歴、鮮度、再開に関する失敗が見つかりやすい。R1/R3/R5が具体化したことには、問題の重要性に加えてこの探索配分が影響している。

ただし、selection effectの大きさを推定できる無作為sampleや対照scanはない。したがって、優先度をそのまま正当化することも、逆に証拠の薄いFamilyへ同量の調査を配ることも根拠が足りない。

| Family | 現在厚い証拠の範囲 | それだけでは言えないこと |
|---|---|---|
| F1 | 参照と展開の分離、buildの条件、依存粒度、cache移行 | AKRの依存を十分に抽出でき、局所改修で再構築費を減らせるか |
| F2 | 管理tool、可変pointer、複数保存先の部分成功、staleな管理情報 | 意味transactionとGit公開を含むregistry全体が他候補より有利か |
| F3 | 追加型記録、実行journal、通知・dedupの境界 | 受理済みdomain eventを意味のauthorityにする構成の適合性。これらの記録は同じ意味ではない |
| F4 | 相反記録、scope、identity移管、複製収束 | 複数authorityの照会・採用・撤回を一体で扱う費用と、中央化に対する利益 |
| F5 | 生成条件等の周辺概念。今回のscanにはgenerator＋独立checker構成の直接調査がない | 仕様中心にする便益、生成器と評価器の共通誤り、仕様変更時の費用 |
| F6 | replay契約、instance互換性、具体的なsignal・restartの修正記録 | AKRの作業にdurable instanceが必要か、短い手順まで導入する費用が見合うか |
| F7 | 不変本文と可変採用情報、logical state、保存inventory、部分取得 | root公開、GC、offline、Gitとの対応を合わせた構成全体の健全性 |
| F8 | 既存の変換・rewriteの概念と、今回のdialect/reader互換性契約 | AKR対象のどの部分に形式化が可能か、意味保存の根拠、変換器維持費 |

全Familyで、AKR上の同条件比較と長期保守費の実測はない。F2/F6/F7の事例の具体性を、Family全体への確信へ変換してはいけない。F5の不足は明確だが、F3/F4にも中核を直接扱う証拠の不足がある。F8は概念上の候補が欠けているというより、AKRへ適用する範囲が未確定である。

### 2.2 証拠を比べる単位

repo数、Issue数、引用数ではなく、次の三つを対応付ける。

1. **問い:** どの候補が異なる予測をするのか。
2. **証拠:** 契約の存在、実装経路、故障条件、実運用の費用、AKRでの結果のどれか。
3. **移せる範囲:** 同じ意味・権限・規模・故障条件がAKRでも成立するか。

同じIssueを複数Familyへmappingしても、独立した支持が増えたとは数えない。失敗報告が多い方式が不安定であるとも、少ない方式が安全であるとも推定しない。実運用報告にも観測されたworkloadの偏りがある。

Family自体も均質な分類ではない。F3/F4はauthorityに、F1/F5/F8は生成・表現に、F6は実行継続に、F7は内容と公開集合に重点がある。併用可能なFamilyを相互排他的な8製品のように比較すると、証拠の配分も歪む。次の実験ではFamily全体を一括で競わせず、**共通の課題・保証・境界を満たす構成**を比較する。今の証拠だけでFamilyの全面再定義は行わない。

## 3. 追加研究の情報価値をどう判定するか

情報価値は、証拠が少ないことだけでは高くならない。次の条件で判断する。

| 条件 | 外部探索を続ける理由になる場合 | 実例・実験へ移す理由になる場合 |
|---|---|---|
| 判断への影響 | 新しい意味単位、保証、変換・保存方式により候補を追加/除外できる | optionは既知で、どれが有効かがAKRの負荷や誤り費用で決まる |
| 外部での判別可能性 | 公開仕様・code・移行記録・独立した運用事例が対立仮説を判別できる | 自然言語資産の損失、実query、実際の保守作業の分布が必要 |
| 今決める必要性 | 直後の試作でidentity/authority/evaluation条件を固定しそう | まだ利用しない機能で、後から分離して調べられる |
| 新規性と重複 | 既読とは異なる境界・失敗・成功条件を得られる | 既知のstale/dedup/移行問題の別実装に留まる |
| anchoring risk | 対照的な機構を同じ問いで調べ、前提差を残せる | 特定repoの語彙や型を、そのままAKRの対象定義にしそう |
| contextと統合費 | 短いclaim・根拠・反例で判断を更新できる | repo詳細が増えるが、候補間で異なる予測が増えない |

現時点では、更新確率や失敗損失を数値で校正できない。点数を作って順位の精密さを演出しない。「この結果ならどの判断が変わるか」を探索前に書く。結果がどちらでも判断が変わらない調査は、優先しない。

## 4. まだ外部探索で更新され得る領域

以下の優先は、この段階で不確実性を減らす手段についてのもの。各能力の恒久的な重要度を採点する表ではない。

| 領域 / 対応 | 外部でまだ変わり得ること | 直ちに必要なAKR側の材料 | 今の扱い・停止条件 |
|---|---|---|---|
| **Managed asset type / boundary、applicability、composition** — D02/03/08〜11、R0/R2/R4、F5/F8にも影響 | 手順、規則、問題仕様、generator、checkerを異なる資産として扱う境界。precondition・作用・停止の合成契約。既存のplanning/制約/変換系で実装された部分問題 | 実際の同じ方法について、入力条件、適用不能、部分合成、局所改修の例 | **限定外部補完の優先候補**。対照的な意味モデルが何を表し、何を拒否するかまで確認。その先のAKR粒度・形式化可能性はR2/R4で判断 |
| **Evaluation / experiment lifecycle、evaluator・dataset・benchmark versioning** — D02/09/15/17/32/36/37/44〜47、R全体 | 評価器変更後の旧score、dataset変化、metric/rubric、judgeや実行構成への依存、評価根拠の失効・比較可能性。生成器とcheckerの依存分離 | 一つの改修について何を成功とするか、評価対象・評価器・入力をどう区別するか | **限定外部補完の優先候補**。後続比較の結論を無効化し得るため。成熟機構の契約が分かれば、評価妥当性・回帰検出力は実例で検査 |
| **Structural / semantic / provenance query、ontology evolution** — D07/09/17/29/33、R4/R7、F4/F8 | unknown、撤回、schema/ontology変更、細かな依存の解釈をqueryへどう露出するか。旧reader・複数scopeとの整合性 | 「何を探したいか」「返すべきでないもの」「未判定」の実query | **問いを先に得てから補完**。OWL/SPARQL等の一般機能説明を追加するより、実queryで既存モデルが異なる答えを返す境界を深掘り |
| **Trust / authorization / revocation / supply chain** — D05/25/26/38〜40/44、R1/R4/R5 | artifactの出自、操作する資格、採用authority、委任・失効の伝播の違い。署名が正しくても使ってよいとは限らない境界 | どの主体が提案・実行・採用できるか、どこへ配布し何を撤回するか | **共有・自動採用・外部作用を扱う比較の前に限定補完**。TUF/SLSA等の既読原理を起点に必要な契約へ絞る。一般的なsecurity全域へ広げない |
| **Skill / package ecosystem、OSS overlap** — D09/13/14/26/38/39、R1/R5/R7 | discovery、依存解決、能力宣言、公開・失効、host適応をどこまで既存部品が実装するか | 一つの登録→検索→改修→検証→公開の必要保証 | **独自実装に入る前の軽い重複確認**。同じ作業の接続境界と不足が分かれば止め、統合費は小さな経路で測る |
| **Model adaptation / lowering / routing、multi-agent handoff** — D13/14/38/42/49、R3/R5/R7 | 意味を保つ変換、非対応の検出、委任時の状態契約には成熟分野の転用余地。新model/harnessの機能一覧自体は変動が速い | 同じM・課題・資産版を使い、tool/context/分担を変えた結果 | **実験中心**。意味保存・状態移送で説明できない失敗が出た範囲だけ外部へ戻る。新しいagent repoの大量比較を先行させない |
| **Long-term industrial lifecycle / configuration baseline / archival / old reader** — D15〜17/26/33/35/41/44/45、R6 | 複数製品・用途・時点のbaseline、変更影響、過去の解釈器を保持する責任と廃止。既読S1000D等は入口に留まる | 何年後に何を復元したいか、失ってよい環境と失えない意味、対象となる候補形式 | **用途が現れた時の限定補完**。現段階では固定構成のcold restore等を先に作れる。規格を網羅することとAKRの保存契約は別 |

最初の二領域を優先する理由は、引用が少ないからだけではない。資産の境界が変わると、登録・依存・query・評価単位が同時に変わる。評価の成立条件が欠けると、後のR1〜R7の成績を同条件で比較できない。この二つは後続研究の判断に広く影響する。

他方、今回のmapで新次元が必要になると予告する根拠はない。既存次元を使って問いを具体化し、その選択肢では説明できない反例が出た場合に限り、次元変更を検討する。

## 5. これ以上広げるより、実例・実験へ移す領域

| 領域 | 既にある判別用の材料 | 次に観測すること | 外部へ戻る条件 |
|---|---|---|---|
| R1 mutation / interface / transaction | stale write、purpose toolでも旧版条件がない経路、payload/history部分成功 | 同じ意味改修をpatch/commandで行い、公開保証、競合検出、修復、総費用を分離 | 必須保証を既知の操作経路で表せない、未調査のtransaction境界が出る |
| R3 event / durable execution | 受領と完了、重複、遅着、自己更新、replay互換、downgrade | 実際に必要な作業で中断・再開を試し、全遷移処理か現在状態への収束かを区別 | AKRで必要な起動意味が既存方式に収まらない、外部作用の保証が未確定 |
| R5 context / materialization / stale state | 同じ版でも展開が別、detach後の残存物、可変採用情報、context引継ぎ | 同じasset版をturn単位で捨てる場合とtask/主体間で継承する場合の差 | bindingsや権限・失効の伝播を現在の経路で観測できない |
| R2 粒度 / composition | 完結手順・primitive・templateという代案は既知 | 実際の局所改修と再利用で、依存・評価・取得の費用と意味損失を比較 | 新しい対象種別で既存の合成意味が破れる |
| R7 retrieval / model adaptation | 候補生成とranking、no-match、interface到達可能性の区別 | 実queryと除外すべき候補で、同一Mの経路交換を比較 | 必要queryを表現できない、新しい意味照会が必要になる |
| R6 preservation / CACの一部 | reader・profile・adapterの分離、旧版共存、変更吸収の試験案 | 依存を一つ失う、補助構造を外す、旧版を再読する。復元可能な意味と費用を観測 | 意味を戻せない、新旧readerの共存契約が不足、保存期間と採用責任が変わる |

これらは「外部調査が完了した」という宣言ではない。既知の機構から、次の小さな比較を作るための情報が揃っているという判断である。新しいfailure modeが出れば、該当する外部契約だけを再確認する。

## 6. R0: 実例を増やす意味と、sampleの偏り

現在の[registry](https://github.com/Authenticationalias/Algorithmic-Knowledge-Runtime/blob/36a38dd1ef6a5fee360ee1b3b2f5f9a9534c87eb/registry/registry.yaml)では、draft algorithm 3件とpolicy 2件を確認した。algorithm本文も読み、現状は自然言語による調査・判断手順が中心であることを確認した。[Blind-Spot Expansion](https://github.com/Authenticationalias/Algorithmic-Knowledge-Runtime/blob/36a38dd1ef6a5fee360ee1b3b2f5f9a9534c87eb/algorithms/reasoning/blind-spot-expansion/algorithm.md)、[Actor-Specific Information Value](https://github.com/Authenticationalias/Algorithmic-Knowledge-Runtime/blob/36a38dd1ef6a5fee360ee1b3b2f5f9a9534c87eb/algorithms/governance/actor-information-value/algorithm.md)、[Secure Information Handling Suitability](https://github.com/Authenticationalias/Algorithmic-Knowledge-Runtime/blob/36a38dd1ef6a5fee360ee1b3b2f5f9a9534c87eb/algorithms/security/secure-information-suitability/algorithm.md)

これは管理対象の観測資料であり、現行Markdown/YAML構成や分類を正解にする根拠ではない。このsampleだけでF5/F8に適した対象が存在しないと結論したり、全algorithmを判断手順に合わせたりすることもできない。

R0は件数の増加そのものを目標にしない。自然に生じた再利用・改修事例から、次の違いを判別できる材料を残す。

- 同じ方法を条件違いで再利用する時、parameter化で足りるか、別のvariantが必要か。
- 局所変更の時、完結した手順と小さな部品のどちらが安全に改修できるか。
- 判断手順、決定的変換、外部作用を含む手順、生成器・評価器に相当する対象が実際に現れるか。
- 何が適用不能で、何が不明で、何をもって改修成功と判定できるか。

今回行った本文・blob SHA照合や、複数担当からの証拠回収は、有限の検証手順や引継ぎの実例として再利用できる。ただし、新algorithmとして登録・採用したわけではない。

自然な実例が不足する部分には、反例用の人工課題を使える。その結果は機構の反証・実行可能性の確認に限定し、実際の作業分布や有用性の推定へ混ぜない。特定Familyが得意な人工課題だけを増やさない。

## 7. OSS overlap / reuse / integrate / build

### 7.1 まだ評価していないこと

既存scanは、再利用できそうな機構を発見した。**既存OSSの組合せがAKRをどこまで代替するかは、まだ評価していない。** 能力の項目数のうち何割を実装済みか、という比率も出せない。項目によって重要度が異なり、接続時に保証が失われる可能性があるためである。

区別したいのは次の三層である。

| 層 | 今ある材料 | 評価すべき残り |
|---|---|---|
| 汎用機構 | 保存、version、query、package、replay、inventory、validation等の既存契約 | 対象版・権限・負荷に適合するか、AIから必要能力を操作できるか |
| 接続・運用 | 各部分のfailure mode、目的別toolや参照固定の例 | ID/版/意味の写像、Gitとの受理境界、欠落・取消・失効の伝播、観測と修復 |
| AKRの意味と採用policy | Purpose/Principles/Constraintsと未決定のD群 | 資産identity、適用・合成・意味変更、評価根拠、採用/廃止の判断をどこで定義するか |

第三層の設計が必要でも、新しいDB、workflow engine、registry、compilerを自作する必要があるとは限らない。configuration、schema/profile、既存policy機構、adapterで表せる可能性を先に調べる。逆に、機構を組み合わせたことだけで第三層が自動的に満たされるとも言えない。

### 7.2 軽い重複確認を実験へ組み込む

最初は、たとえば「候補を取得し、適用条件を確認し、基準版に対して改修し、評価根拠とともに公開する」という一つの作業を対象にする。これは固定したAKR実装pipelineではなく、複数候補を比較する課題である。

各候補構成について、以下を一枚の対応表にする。

1. 必要な操作と保証。
2. 既存componentが公開する契約、固定版、確認根拠。
3. その契約がAIのtool経路へ露出されるか。
4. component間で保持すべきidentity、revision、権限、評価・採用状態。
5. configurationで足りる部分、adapter等を要する部分、機構自体が不足する部分、未確認。
6. upgrade、失効、停止、component交換時に残る独自保守。

既読のRegistry/管理tool、DVC等の参照と展開、durable workflow、MLIR等は、該当する部分契約の候補資料になる。これらを一括で採用する案にはしない。外部service依存、配布条件、ライセンス等も、具体的採用候補になった範囲で確認する。

仕様上必須保証が欠けるなら、その構成は除外するか不足を明示する。仕様が合っていても統合費が不明なら、最小の接続だけを検証する。全Familyの完成実装を作ってから比較する必要はない。

独自実装へ進む条件は、必要な意味・保証が既存の構成では満たせない、または満たすための継続保守が比較対象より重いという証拠である。独自実装を選ぶ場合にも、その範囲を不足する境界へ限定できるかを検討する。現時点でAKR独自部分を確定しない。

## 8. 次に進む方法の比較

| 進み方 | 得られる情報 | 現在の弱点・費用 | 判断 |
|---|---|---|---|
| 全領域のLandscape Gap-Closure | 広い候補・未知の反例 | closureを保証できず、同種証拠・context・統合費が増える。実対象の不明は解決しない | 採らない |
| 証拠の薄いFamilyへ均等補完 | F5/F8等の具体像 | Familyの切り方と引用量に研究配分が引かれる。F3/F4の中核不足も見落とし得る | 問いを単位にする形へ変更 |
| R1/R3/R5だけを直ちに比較 | 経路・停止・鮮度の実際の失敗 | 資産境界や評価条件が弱いと、機構の動作をArchitecture適合性と取り違える | 機構確認は進められる。Family選択は早い |
| R0だけで登録を増やす | 実際の対象、query、変更分布 | 現在と同じ判断手順が増えるだけでは対象の偏りが残る | 対立仮説を判別する事例として収集 |
| OSS overlapを全面先行 | 重複機構と候補構成 | AKR側の必要保証が曖昧だと機能表になる。組合せ探索も膨張 | 小さな作業単位で実験準備に組み込む |
| 地図を固定し、問題が出るまで待つ | 文書・分類のchurnを抑える | 意味・評価・採用境界の未確定が無意識に実装へ固定され得る | 地図は暫定安定化。構造を変える問いは先に絞って調べる |
| **限定補完＋実例＋小比較** | 意味・評価の前提を補い、既知の機構は実対象で判別できる | 両作業の境界と終了条件を管理する必要 | **現時点の推奨** |

### 8.1 推奨する次の研究単位

順番は実行を拘束する計画ではなく、情報依存を示す。

1. **判別用の実例を置く。** R0/R2/R4から、対象、変更、適用不能、必要な意味保証を少数の実例で明確にする。Familyごとに都合のよい別課題を置かない。
2. **二つの穴を限定補完する。** 資産の意味・適用・合成と、評価器/dataset/評価根拠のlifecycle。問いごとに、対照的な機構を持つ少数の実装・標準と運用例を確認する。最初の枠を越える時は、増える調査がどの判断を変えるかを説明する。
3. **同じ実例で小比較を始める。** R1/R5を中心に、必要保証と経路を比較する。R3は、再実行だけでは失われる途中状態、対話継続、長期instance、外部作用のいずれかが問題になる場合に接続する。OSS overlap表を同じ作業の準備として作る。
4. **結果に応じて追加探索を開く。** 意味照会ならR7とontology、権限委任・配布ならtrust、読取器喪失ならR6と長期lifecycleへ絞る。

単なる機構確認であれば、1と2の完了を待たずにR1の条件付き更新等を確認できる。その成功を最終Architectureの選択根拠へ拡大する段階で、意味と評価の前提が必要になる。

### 8.2 前回R0〜R7との差分

- **R0:** 継続。件数より、実際の適用・改修・中断と未解決の意味を残す。
- **R1:** 先行を維持。ただし「現経路の必要保証を確認する先行」と「Familyを選ぶ先行」を分ける。
- **R2/R4:** 資産境界・合成・共通化の小さな事例整理を、Family比較の前提として前へ出す。全文の再導出ではない。
- **R3:** 既知の故障機構は十分に具体化した。途中状態、対話継続、長期instance、外部作用の保持が必要な範囲で早める。今回の途中成果回収・引継ぎ停止もその一例なので、短い中断・再開比較は既に有用である。durable engine全体の採用判断は分ける。platformの機能増加だけで常に最優先にはしない。
- **R5:** 引き続き早い小比較に向く。今回の引継ぎ・contextの観測と、資産利用の広い範囲に関係する。
- **R6:** 候補形式や旧reader、採用履歴を失う具体的条件で比較する。全産業の保存規格を先に網羅しない。
- **R7:** 実queryを先に得る。同一Mのharness/context交換を比較し、必要queryの意味が既存モデルを超える場合に外部へ戻る。

評価器・dataset等のversioningは、R8という独立順位にせず、D37等に基づくR1〜R7の比較条件として補う。D番号とF定義は今回変更しない。前回のR3早期化を無条件の一般順位に拡大せず、適用条件を明記した更新である。

## 9. 探索を止める条件、再開する条件

限定外部補完の終了条件は「その領域を網羅した」ではない。

- 候補が異なる予測をする意味・保証・失敗条件を示せた。
- 新しい資料が既知の条件の別実装に留まり、次の比較内容を変えなくなった。
- 残る不確実性の中心が、AKRの対象・query・変更頻度・誤り費用へ移った。

実験も、動作確認を増やし続けない。必要保証を欠く候補、未判定の意味、次に測るべき費用の違いが分かれば、その小課題の目的は達したとする。少数例から一般優位性は主張しない。

探索を再開するtriggerは、新しい資産種別、既存の合成意味で表せない作用、未表現のquery、委任・失効境界、依存の喪失、componentの変更である。単に新repoや新modelが出たことは、それだけではtriggerにしない。

## 10. 研究構成、anchoring、context費

今回の追補では、Family証拠の抜粋と、問い別の必要証拠の抜粋だけを二担当へ委任した。新しいrepo探索は行わせず、各々53行・43行の成果を先に保存した。leadは元の基準、現在の登録事例、抜粋の限定を確認して判断を統合した。これもmodel間の費用・性能比較ではない。

次の外部補完を行う場合、workerへ渡すのは全Architectureの結論ではなく、判別したい問い、必要保証、反例、既読資料と除外範囲でよい。証拠packetには、短いclaim、固定参照、証拠種別、成立条件、反証・未確認、どの判断に使えるかを残す。候補mappingは暫定と明示し、leadが再判定する。

leadの直接確認が必要なのは、資料が資産の意味やauthorityを変える、既存次元へ吸収できない反例が出る、sourceの世代や保証が曖昧、またはその証拠で候補を除外・採用しそうな場合である。高度なmodelであることだけを理由に全量探索を集約しない。

停止時の引継ぎを確保するため、workerは調査の最後まで成果保存を待たない。共通quotaを前提に、分業数を増やしても独立した継続性が得られるとは扱わない。leadへ渡す量を抑えても、根拠へ戻れる参照を残し、短い要約だけでの誤採用を防ぐ。

anchoringを抑える確認は次の三つに絞る。

1. 同じAKRの問いと保証を、異なる機構の資料にも当てる。
2. product固有のentity名・schemaを使わず、発見した契約を説明できるか確認する。
3. そのprojectを候補から外しても、研究上の問いが残るか確認する。

**結論として、次の研究対象は「証拠の薄いrepo領域」そのものではなく、まだ判断を変え得る問いである。** 外部で機構や意味モデルを補う価値が高い部分を絞り、既知の機構の有用性はAKRの実例へ移して判断する。
