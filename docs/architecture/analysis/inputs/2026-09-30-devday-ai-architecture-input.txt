# 9. 重要な修正：SpaceはLibraryの後継ではない

議論途中でSpaceを「Libraryの後継」と表現したが、これは修正。

2026-09-30現在、**Libraryは独立機能として存続している。**

Libraryでは、

- ChatGPTへuploadしたfile
- ChatGPTが生成したfile
- Google Drive等の接続file

を検索・再利用できる。

PlusのLibrary容量は20GB。

Google Drive fileはLibrary内に見えるが、Drive上の原本との接続を維持する。

したがって現在は、

**Library = file / asset layer**

**Space = shared working-context / collaborative workspace**

と区別する。

将来的に両者が統合される可能性はあるが、現在のAuthority設計では前提にしない。

# 10. Library + Google Driveの既存価値

↕
Google Drive

つまり、

ChatGPT内部生成data
+
Google Drive上の外部data

をAIが比較的同じinterfaceから扱える点は引き続き価値がある。

Space追加後も、この機能は消えていない。

# 15. 現在のレイヤー分離

現在の最も有力な整理。

## Layer 1：Authority / Persistent Data

長期的な原本・意味・履歴。

候補：

- Git / GitHub
- Local Git
- SQLite
- Google Drive

ここを特定AIベンダーのworkspaceだけに依存させない。

---

## Layer 2：Representation / Data Format

用途別形式。

Human-readable：

- Markdown
- YAML

Structured semantic state：

- SQLite

Interchange：

- JSON / JSONL

大量分析：

- Parquet
- DuckDB

Office / document：

- Google Docs
- Sheets
- Slides
- PDF

Semantic retrieval：

- embeddings
- vector index

一種類に統一する必要はない。

---

## Layer 3：Access

AIがAuthorityへ到達するためのlayer。

- MCP
- Plugins
- GitHub connector
- Google Drive connector/API

特に重要：

**MCPはStorageではない。**

MCPは、

「AIがStorageやapplicationへアクセス・操作するためのprotocol/interface」

として扱う。

したがって、

SQLite vs MCP

という比較はしない。

---

## Layer 4：Working Context

現在進行中の仕事をAIと人間が共有する面。

- ChatGPT Library
- ChatGPT Space
- Pages

ただしLibraryとSpaceは役割が違う。

Library：
file asset / retrieval

Space：
shared working context / workspace

---

## Layer 5：Execution

実際に作業するagent/runtime。

- ChatGPT Work
- Codex
- Automations
- Dots
- Agents API
- Local AI

---

## Layer 6：UI

人間とのinteraction surface。

- ChatGPT
- Plugin Extensions
- Codex Desktop
- CLI
- Open WebUI
- custom local web UI

# 16. GitHubとLocal Git

このチャットでは、

「GitHubに置くかPC内部に置くか」

という問題も出た。

結論：

**二者択一ではない。**

Gitは分散型なので、

Mac
└─ Local Git
     ↓ push/pull
GitHub

という構造が本来の使い方。

Local cloneもrepository履歴を持つ。

可能な構成：

### GitHub canonical

GitHub
= canonical authority

Local Git
= clone / execution environment

利点：

- cloud AIからアクセス容易
- Codex/GitHub連携
- version sharing
- CI
- multi-agent interoperability

### Local canonical

Local Git
= canonical authority

GitHub
= replication / collaboration / selected publishing

利点：

- privacy
- offline
- vendor independence

したがって今後は、

「GitHubかLocalか」

ではなく、

**何をどこまでremote replicaへ出すか**

という問題になる。

# 17. SQLite

SQLiteは依然有力。

役割は単純なfile storageではなく、

**structured semantic state**

として考える。

例：

- Entity
- Relationship
- Evidence
- Source
- Decision
- Dependency
- Status
- Version
- Confidence
- Provenance
- Algorithm

Markdownだけで長期運用すると、

- relation
- duplication
- query
- status
- provenance
- machine update

の管理が難しくなる。

SQLiteはこの層を担当できる。

---

# 18. SQLite + MCP

SQLite fileそのものをモデルに毎回渡す必要はない。

MCP経由で例えば、

- get_schema
- search_entities
- get_entity
- get_relationships
- append_evidence
- update_status
- query
- export

などをtool化できる。

構造：

SQLite
↓
MCP server
↓
ChatGPT / Codex / Local AI / 他AI

利点：

- schemaを隠蔽できる
- AIに直接SQLを書かせなくてもよい
- read/write権限を限定できる
- 複数AIから共通利用できる
- DB内部構造変更の影響を吸収できる

---

# 19. SQLite + Git

SQLiteだけでは人間可読のdiffやGit履歴との相性に課題がある。

そこで、

SQLite
↓ export
Markdown / JSONL
↓
Git

という二重表現も候補。

つまり、

SQLite
= machine-oriented structured state

Git-tracked Markdown / JSONL
= human-readable lineage / interchange

という役割分担。

これはまだ確定案ではなく検討候補。

## 一文要約

DevDay 2026によって既存構成が置き換えられたのではなく、OpenAI側に**永続agent・event-driven execution・shared AI workspace・ChatGPT内拡張UI**という新しい面が追加された。

現在の方針は、それらをGit / SQLite / Google Drive等のベンダー非依存Authorityの上に載せ、ChatGPT固有のLibrary / Space / Codexを作業・実行・UI層として使う構造を検討すること。
