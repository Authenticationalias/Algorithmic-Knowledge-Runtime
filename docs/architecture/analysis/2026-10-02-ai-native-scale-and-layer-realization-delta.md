# AKR: AI-native・容量規模・層への実現粒度の前提確認

2026-10-02 JST · upstream assumption clarification / analysis draft

## 0. 結論

**AIが主要な利用者・保守者である前提は維持する。今回の追加は、容量・配置・共通化の範囲・Architectureの分割粒度を、同じ保守課題で比較できる条件へ具体化することである。**

既存のPurpose / Principles / Constraints、D01〜D49、F1〜F8、R0〜R7は基準として引き継ぐ。数百GB、TB、PBは探索する規模条件として扱う。現在の保有量や、初期運用でPBを必須とする要求だとは解釈しない。

直近の小比較は局所的な契約の確認であり、上流探索をそこへ縮小する根拠ではない。特定会社の推奨形、既存OSS、現在のmodel/harness、Drive/GitHub/SSDの現在の使い勝手を、最適Architectureの前提にしない。

新しいCanonical、DB、IR、schema、保存先・製品、数値の切替閾値は今回決めない。

## 1. 入力と既存分析との差分

基準head: `8e20b09e3994dfb58fede84a894af833847632bf`、draft PR #1。

今回のユーザー指摘:

- AI-native時代の前提を、従来の情報・製品側の設計前提から独立させる。
- 数百GB、TB、PB等、情報規模によって適する構成が変わり得る。
- cloud drive、GitHub、外部SSD等の配置を含める。
- 基礎理論を明確にし、各layerへ実現する責務と粒度にも複数の方法論がある。
- 広い互換性を持つ「パーソナル型」、layerに適合させる型等を候補として残す。

「パーソナル型」の具体的範囲は確認中である。以下では、個人の複数環境を横断する型と、より広い環境互換を重視する型を候補として残し、語の意味を新しいhard constraintにしない。「すべて互換」も範囲未指定の実装保証とは扱わない。

| 論点 | 既にある根拠 | 今回具体化する不足 |
|---|---|---|
| AI-native | [Coverage §6.2/§8/§9](./2026-09-29-architecture-search-space-coverage-audit.md) | 人間向け保守前提を外した時の候補再評価と、AI操作経路全体の費用 |
| 規模 | Coverage §9.1/9.2のN/E/R・更新率・変更波及・writer数 | bytes、稼働集合、object数、派生物/履歴、取得・復元量を組み合わせた負荷profile |
| 配置 | D23〜31/41〜43、F1/F7、[Delta §9](./2026-09-30-external-landscape-assumption-delta-audit.md) | 複数保存先をまたぐ固定版取得、公開の部分成功、旧版復元 |
| 共通化・互換 | [実運用評価 §3〜7](./2026-09-29-production-driven-architecture-evaluation.md)、F4/F8、profile/adapter/CAC | 環境全体の横断とlayer適合を優先する方法論の同条件比較 |
| 層への分割 | Coverage §3、Interface経路、CAC | 資産粒度とArchitecture責務の分割粒度を分けて比較 |

別担当による該当箇所の読取照合も行った。新しい外部資料・製品仕様・性能証拠は追加していない。全面Coverage Auditや、既済み工程のやり直しは行わない。

## 2. AI-nativeを比較前提にする

AI-nativeは、既存の操作をAIへ置き換えるだけの前提ではない。AIによる対象特定、構造化、query、局所変更、tool/adapter生成、検査、repair、migration、廃止管理を通じて、長期保守の費用と保証を比較する。

| 先に正解にしない前提 | AI-nativeで比較する問い |
|---|---|
| 人間が手で書きやすいtextを優先 | machine-oriented構造、binary、IR、型付き操作でも、AIが意味を取得・変更・検査できるか |
| 多数のadapter/schemaは人間の維持負担が大きい | AI生成・増分更新・回帰検査を含め、広い互換性の便益が全維持費を上回るか |
| 検索結果を人間が整理してから再利用 | AIが適用条件・依存・未判定・利用許可を機械的に確認し、必要集合だけ取得できるか |
| migrationは稀な一括移行 | 段階移行、旧新reader、候補固有の意味、用途別採用をAIが継続管理できるか |
| 現在のharnessに合わせて資産を記述 | 上位の意味・identity・lineageを保ち、profile/adapter等の交換で変化を吸収できるか |

既存方式については、次の三つを分ける。

1. **成立原理・必要保証:** 整合性、依存、固定版、故障、権限、復元等。AIが操作しても、何を保証するかを明示する必要は残る。
2. **運用上の前提:** 手編集、固定schemaの手保守、UIによる選択等。AKRへそのまま持ち込まない。
3. **実装と推奨構成:** ある負荷・主体・製品で選ばれた組合せ。AKRのAI保守条件で再評価する。

会社名や設計年代だけで、個々の原理・製品をAI-native/非AI-nativeと一括判定しない。同時に、成熟した方式であることからAKRへの適合を導かない。AIが生成できるという可能性と、維持・検査・移行が低費用になる実証も分ける。

## 3. 数百GB / TB / PBを何の規模として扱うか

総bytesとalgorithm件数は別である。原資料、dataset、model/実行artifact、trace、派生表現、履歴・複製がbytesを占める場合もあり、すべてを同じ意味資産やmodel contextとして扱わない。

規模profileには、少なくとも次の違いを記録する。固定schemaの採用ではない。

- 意味上の資産・系統数、object数、依存数と構造。
- 原資料、意味表現、派生物、評価証拠、履歴、複製の容量内訳。
- 実際に稼働する集合、taskごとの取得集合、必要依存closure。
- 更新率、writer数、一変更での再生成・再評価範囲。
- 保管場所、接続状態、アクセス権限、取得・転送・復元量。
- 許容する遅延、鮮度、欠落、復旧時間、保持する意味・証拠。
- model/harnessが取得・操作できる経路と資源予算。

| 同程度の容量でも異なる仮想負荷 | 候補を変え得る論点 |
|---|---|
| 少数の大きな不変payload | 本文の部分取得、転送、保持・復元。管理metadataの更新は小さい場合がある |
| 多数の小さな資産・関係 | object/参照数、query、索引、batch、整合更新、公開集合 |
| 多くの派生物と長い履歴 | 生成条件、失効、再生成、保持/GC、旧readerと証拠復元 |
| 更新が依存graphへ広く波及 | 再検査閉包、queue、優先度、未完了、意味変更の伝播 |

これらは比較条件の例であり、実際のAKR負荷・成績ではない。GB/TB/PBだけで特定DBや保存先を割り当てる閾値は決めない。PB全体を保管していても、各taskの意味資産・取得集合が小さい構成は検討可能である。逆に本文量が小さくても、関係と更新の密度で保守負荷が増える場合を試す。

## 4. cloud drive / GitHub / SSDの役割を分けて比較する

GitHubを変更履歴・version・branch・rollbackの管理基盤として使うhard constraintは維持する。それだけから全payloadをGitHub内に置く設計は導かない。

| 論理上の責務 | 配置候補を比較する時の問い |
|---|---|
| 意味の根拠・用途別採用 | どの固定資料・版・scopeが利用判断を定めるか |
| 変更履歴・公開集合 | GitHubの固定commitから、どの外部内容・reader・依存を特定できるか |
| 大容量payload・原資料 | Drive、SSD、他の外部store等で、固定版を取得・保持・復元できるか |
| index/cache/派生表現 | 上流の何から生成され、破損・失効時にどこまで再構築できるか |
| working context / 実行state | taskに何をbindingし、別の場所・主体へ何を引き継ぐか |

同じ保存先が複数の責務を担う場合も、責務が複数の保存先へ分かれる場合も候補にする。Drive=UI、SSD=cache、GitHub=唯一の意味正本と固定しない。場所の利便性からauthorityを推定しない。

外部payloadを使う候補では、Git上の参照・digestだけではbytesを復元できない。保持先、実体、reader、解釈、許可された採用scopeが必要である。Git公開と外部store更新の同時成功を仮定せず、部分成功・照合・再試行・公開拒否・旧版復元を比較する。

Google Driveで旧環境を残して整備中という前回の報告は、引き続き並存・移行の実例候補である。具体的なauthority、現在容量、旧新scope、同期・実行結果は未確認であり、今回の容量例をその環境の現状へ当てはめない。

## 5. 方法論と層へ戻す粒度も候補として残す

以下はF1〜F8を置換するfamilyではなく、候補を組み立てる上位の方針である。併用可能で、同じ分類階層の相互排他的な製品ではない。

| 方針候補 | 比較する便益と費用 |
|---|---|
| 共通の論理・契約から各layerへ実現 | 規範・検査の共有、生成・変換の一貫性。共通モデルの表現限界と移行波及 |
| 個人の複数環境を横断する共通管理とnative保持 | 環境交換・個人資産の継続利用。意味対応・adapter・権限・旧新並存の維持費 |
| layer/domain固有契約に適合する構成 | 下位機構の能力を使い、局所変更する。境界間の意味・状態・作用の対応と再検証 |
| 規模・用途に応じてprofileを切り替える構成 | 同じ意味を条件別に利用する。profile選択、移行中の重複維持、保証と採用scopeの差 |

Architectureの分割粒度は、asset粒度だけではない。意味・更新・検査・公開・取得・実行・復元の各責務を、どの単位と境界へ割り付けるかである。D03だけで比較済みとは扱わず、D05/06/14/18/21/23/32/38/43/46/49の結合として具体化する。

方法論には、理論から必要保証と層を導く経路、具体的な利用・故障から契約と境界を見いだす経路、既存機構へ保証を割り付ける経路、その往復がある。どの経路も、現在の実装を最初に正解にして他候補をそこへ正規化する必要はない。

「基礎理論の完成」は、必要能力、意味上の不変条件、authority、失敗、互換性、未決定境界を明確にする研究として扱う。現時点で普遍的な理論が完成したとは言えない。論理上の整合性と、具体的経路で保証・費用が成立することを分け、理論化と実例検査を往復する。今の操作の都合で上流の選択肢を閉じない。

## 6. 互換性を一つのbooleanにしない

「すべて互換」という目標は、次の保証へ分けて比較する。

1. 固定内容の保存・取得・読取。
2. 値・構造・未知fieldの保持。
3. 適用条件・手順・停止・不確実性の保持。
4. 状態・外部作用・再開・補償の対応。
5. 更新・権限・採用scope・版の対応。
6. model/harness/runtime交換後の利用、旧reader、将来migration。

対象範囲を指定し、完全対応・部分対応・非対応・未判定を区別する。外部環境や将来方式への対応を未検証のまま保証しない。nativeの資料を固定保存して対応保留にすることも、共通モデルへ変換することも候補に残す。

AIがconverterやadapterを生成する案は排除しない。対応する数の多さだけで便益を判定せず、意味保存の検査、変更波及、回帰、repair、旧版維持、補助構造を外す費用を含める。Change Absorption Capacityは引き続き横断評価属性である。

## 7. 今回更新する研究条件

| 研究 | 必要な差分 |
|---|---|
| R0 | 現在容量・資産数・更新/利用・保存内訳を、確認できた範囲で分ける。大容量を仮想profileと現保有量で混同しない |
| R2/R4 | asset粒度に加えて責務の分割粒度、共通モデル/native、互換性の範囲を同じ原資料・改修で比較 |
| R1/R3/R5 | 保存先をまたぐ公開・取得・部分成功、active集合、連続更新・変更閉包を比較 |
| R6 | 層境界や規模profileを変更し、外部payload・旧reader・採用判断を復元する条件を加える |
| R7 | 同じ意味・品質・予算でmodel/harness/tool/取得経路を替え、backend容量と実際に利用できる能力を分ける |

最初から数百GB〜PBを物理的に用意する必要はない。原理・部分故障は小例で検査し、容量・object数・転送・queue・復元の限界は必要な負荷で別途測る。小例の成功を大容量対応の実証へ拡張しない。

D01〜D49を維持する今回の判断は、列挙した問いを既存次元の結合として表せるためであり、上位の方法論比較を終了したという意味ではない。既存組合せで表せない保証・責務が現れれば、独立次元やFamily変更を再検討する。

今回追加したのは比較条件と解釈の明確化である。AI-nativeの前提、GitHub管理、model/environment independence、意味と派生表現の分離、長期保守・migration、現在の形式への非anchoringを維持する。容量別の最終構成、普遍的な共通理論、全環境の互換性は未決定である。
